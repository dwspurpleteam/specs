# Манифест плагина 1.1

Манифест описывает постоянные свойства одной версии плагина: интерфейс, точки взаимодействия с backend, необходимые данные звонка и публикуемые результаты. Реестр хранит его как неизменяемый JSON. Изменение адресов, требований или возможностей плагина требует новой `plugin-version`.

Это целевой контракт версии `1.1`. Он расширяет [формат 1.0](plugin-manifest-v1.0.md) полями, необходимыми плагину посещаемости. Манифесты версий `0.1` и `1.0` требуют явного преобразования в `1.1`; одного изменения номера версии недостаточно. Описание формата `1.0` сохраняется в отдельном файле.

Машиночитаемое описание: [plugin-manifest-v1.1.schema.json](plugin-manifest-v1.1.schema.json). Общая архитектура запуска, проверки контекста и доставки результатов описана в [spec.md](spec.md).

## Пример для посещаемости

Адреса соответствуют конфигурации публикации посещаемости в `deployer`, `plugin-version` — версии в `backend/gradle.properties` плагина. Это подготовленный манифест для интеграции: наличие адреса не подтверждает реализацию всего целевого контракта демо-сборкой. В частности, обработчик `/platform/control` и получение начального состава ещё предстоит реализовать. Перед публикацией следует проверить соответствие реализации манифесту и указать версию выпускаемой сборки.

```json
{
  "manifest-version": "1.1",
  "plugin-id": "attendance",
  "plugin-version": "0.1.0",
  "name": "Посещаемость",
  "description": "Учёт присутствия участников с момента подключения плагина к звонку",
  "frontend": {
    "url-web": "https://calls.vareonix.cc/apps/plugin-attendance/"
  },
  "backend": {
    "health-url": "https://calls.vareonix.cc/apps/plugin-attendance/actuator/health",
    "control-url": "https://calls.vareonix.cc/apps/plugin-attendance/platform/control",
    "initial-state": ["participants"],
    "events": {
      "available-event-types": [
        "participant.joined",
        "participant.left",
        "call.ended"
      ]
    },
    "media": {
      "input": [],
      "output": []
    },
    "results": {
      "keys": ["attendance.summary"],
      "delivery-report-url": "https://calls.vareonix.cc/apps/plugin-attendance/platform/deliveries"
    }
  }
}
```

## Общие поля

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `manifest-version` | string | Да | Для этого контракта строго `1.1`. |
| `plugin-id` | string | Да | Постоянный идентификатор плагина в реестре. |
| `plugin-version` | string | Да | Неизменяемая версия плагина; рекомендуется SemVer. |
| `name` | string | Да | Название в каталоге. |
| `description` | string | Нет | Описание в каталоге. |
| `frontend` | object | Да | Настройки интерфейса в iframe. |
| `backend` | object | Да | Точки взаимодействия и требования backend. |

Строки, если не оговорено иное, непустые и содержат хотя бы один непробельный символ. Элементы списков не повторяются. Неизвестные поля и неподдерживаемые обязательные требования отклоняются: игнорирование требования не должно приводить к запуску с неполными данными.

Списки событий, начальных данных, медиа и ключей результатов описывают запрашиваемые возможности. Они сами по себе не выдают разрешений. Фактические права конкретной активации определяет платформа; доступ за пределами объявления манифеста не разрешается.

## Кто использует поля

Разработчик передаёт данные манифеста в реестр. Реестр проверяет структуру и сохраняет описание версии; каталог и Plugin Manager получают его оттуда. Реестр не запускает backend, не принимает бизнес-результаты и не доставляет события. Ниже указаны логические потребители целевого контракта; это не утверждение о готовности текущих реализаций сервисов.

| Поле | Кто читает | Что делает и кто принимает запрос |
| --- | --- | --- |
| `manifest-version` | Реестр, Plugin Manager, клиент каталога | Выбирают правила разбора и проверяют, что поддерживают формат. Это версия структуры документа. |
| `plugin-id` | Реестр, каталог, Plugin Manager | Находят плагин, связывают его версии и активации. Идентификатор остаётся одним и тем же при обновлении сборки. |
| `plugin-version` | Реестр, Plugin Manager | Хранят и выбирают конкретную неизменяемую конфигурацию; Plugin Manager фиксирует выбранную версию для активации. Это версия плагина, а не схемы манифеста. |
| `name`, `description` | Каталог и UI Adapter в Meet | Показывают пользователю название и описание. Название можно менять независимо от постоянного ID при выпуске новой версии. |
| `frontend.url-web` | UI Adapter в Meet, затем браузер | Адаптер устанавливает адрес iframe. Браузер делает GET страницы; её принимает HTTP-сервер плагина и возвращает frontend. |
| `frontend.sdk-version` | Реестр и потребители метаданных SDK | Сообщает, какую библиотеку использует интерфейс. Само поле не загружает библиотеку и не подтверждает поддержку контрактов. |
| `backend.sdk-version` | Реестр и потребители метаданных SDK | Сообщает фактическую версию серверной библиотеки. Самостоятельная реализация протокола допускает отсутствие поля. |
| `backend.health-url` | Plugin Manager или его проверяющий компонент | Выполняет GET; HTTP-обработчик backend плагина возвращает состояние процесса. Для посещаемости это Spring Boot Actuator. |
| `backend.control-url` | Plugin Manager или компонент доставки управляющих сообщений | Отправляет POST; backend плагина принимает команду для конкретной активации. Запуск означает начало обработки звонка в уже развёрнутом приложении, а не запуск контейнера или JVM. |
| `backend.initial-state` | Plugin Manager | Проверяет доступность необходимых начальных данных и организует их передачу из адаптера платформы в backend плагина. Массив содержит названия наборов данных; сами участники передаются при запуске. |
| `backend.events.available-event-types` | Plugin Manager, сервис доставки событий, backend плагина | Менеджер определяет допустимые типы; сервис доставки фильтрует поток; backend обрабатывает разрешённые события. Фильтр фактической подписки не может расширять выданный доступ. |
| `backend.events.available-event-groups` | Plugin Manager и сервис доставки событий | Разворачивают запрошенные группы по каталогу событий. Если указаны конкретные типы, группы не используются. |
| `backend.media.input` | Plugin Manager и сервис доставки медиа | Разрешают перечисленные входящие потоки; backend плагина принимает их через SDK. Пустой список не создаёт медиаподписку. |
| `backend.media.output` | Plugin Manager и компонент публикации медиа | Разрешают перечисленные исходящие потоки, которые backend плагина публикует через платформу. Пустой список не запрашивает публикацию. |
| `backend.results.keys` | Plugin Manager и Result Gateway | Определяют разрешённые ключи результатов. Плагин отправляет результат в Result Gateway, который проверяет сообщение совместно с менеджером и организует доставку адресатам. Это не адрес и не HTTP-маршрут. |
| `backend.results.delivery-report-url` | Result Gateway или его компонент доставки отчётов | Отправляет POST с отчётом о результате; backend плагина принимает статус доставки. Это обратное направление относительно публикации результата в Result Gateway. |

Backend и SDK не обязаны читать файл манифеста самостоятельно. Менеджер использует зарегистрированный документ для организации запуска; приложение реализует объявленные обработчики и работает с переданными параметрами активации. Собственный REST API между frontend и backend плагина, например `/api/calls/{callId}/participants`, в манифесте не перечисляется: платформе не нужно вызывать внутренние бизнес-методы плагина.

## Область подключения

В текущем контракте все плагины подключаются на звонок (`per-call`). Открытые участниками интерфейсы используют общее состояние соответствующей активации. Это общее правило платформы, поэтому поле `activation.scope` в манифесте отсутствует. Подключения на пользователя (`per-user`) потребуют отдельного расширения контракта.

Каждая активация имеет собственный `activationId`; его нельзя заменять `callId`. Пользователь, запросивший подключение (`requestedBy`), является инициатором, а не областью обработки. Повторная доставка команды запуска с тем же `activationId` не создаёт дополнительный трекер или подписку. Разные плагины в одном звонке имеют разные активации; новая активация после остановки также получает отдельный идентификатор.

Открытие и закрытие iframe не запускает и не останавливает обработку данных. При отключении активации, завершении звонка или отзыве разрешения обработка и публикация прекращаются. Произвольная политика остановки по отсутствию запросов UI в этот контракт не входит.

## Frontend

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `frontend.url-web` | string, URI | Да | Абсолютный HTTPS-адрес страницы плагина. |
| `frontend.sdk-version` | string | Нет | Фактически используемая версия Frontend SDK. При отсутствии SDK поле не указывается. |

В `url-web` не включаются идентификаторы конкретного звонка, активации, участника и токены. Подписанный контекст передаётся после готовности страницы через bridge, как описано в общей архитектуре. Версия библиотеки SDK не заменяет версию контракта и проверку доступных возможностей.

Если ассеты и API используют относительные пути, адрес страницы должен заканчиваться на `/`. Origin интерфейса определяется из `url-web`; ограничения встраивания и проверки отправителя сообщений остаются частью общего контракта платформы.

## Backend и управление активацией

| Поле | Тип | Обязательность | Значение при отсутствии / назначение |
| --- | --- | --- | --- |
| `backend.health-url` | string, URI | Да | Абсолютный HTTPS-адрес проверки доступности приложения, вызываемый методом GET. |
| `backend.control-url` | string, URI | Да | Абсолютный HTTPS-адрес приёма управляющих сообщений методом POST: запуск и остановка активации, приостановление и возобновление. |
| `backend.sdk-version` | string | Нет | Не указывается, если Backend SDK не используется. |
| `backend.initial-state` | string[] | Нет | `[]`: начальные данные не запрашиваются. |
| `backend.events` | object | Нет | Подписка на события не запрашивается. |
| `backend.media` | object | Нет | Входящие и исходящие медиа не запрашиваются. |
| `backend.results` | object | Нет | Публикация результатов через платформу не запрашивается. |

Положительный healthcheck подтверждает доступность процесса, но не готовность конкретной активации. Backend подтверждает готовность после получения необходимых начальных данных и установки подписок. Управляющие запросы проверяются по правилам подписей и защиты от повторов из общей архитектуры. Завершение доступа платформой не зависит от ответа плагина на команду остановки.

Тело управляющего сообщения и формат подтверждения определяются контрактом управления активациями. Манифест объявляет адрес обработчика и его требования, а не отдельный протокол для каждого плагина.

## Начальные данные

В `backend.initial-state` в этой версии поддерживается значение `participants`: текущий состав участников звонка на начало учёта. Это обязательное требование при его объявлении, а не необязательная подсказка.

Для каждого участника нужны стабильный `participantId` и, если доступно, отображаемое имя. Служебные подключения платформы не входят в пользовательский состав. Получение списка не должно требовать от плагина доступа к LiveKit или восстановления имени из `participantId`.

Начальный состав и поток событий должны быть согласованы по моменту начала учёта: изменения между получением состава и подпиской не теряются и не применяются дважды. Конкретный механизм согласования определяется API источника данных. Если платформа не может обеспечить объявленные начальные данные и согласование, активация завершается ошибкой.

Посещаемость считает время с успешной инициализации учёта (`trackingSince`). Участник, уже присутствующий в начальном составе, учитывается с `trackingSince`; это не его фактическое время входа в звонок. История до подключения не запрашивается. После разрыва потока восстановление текущего состава не восстанавливает потерянные интервалы посещений: такие интервалы должны оставаться отмеченными как неполные.

## События

Транспорт событий фиксирован общим контрактом платформы: backend плагина открывает gRPC-подписку `EventService.Subscribe` на streamapi напрямую или через Backend SDK. Поэтому поле `transport` не требуется. HTTP-доставка событий в backend плагина в этой версии не предусмотрена.

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `backend.events.available-event-types` | string[] | Хотя бы один из двух списков | Точные типы событий. |
| `backend.events.available-event-groups` | string[] | Хотя бы один из двух списков | Группы событий из каталога платформы. |

Каждый указанный список непустой. Если указаны оба списка, используются только конкретные `available-event-types`, как и в прежнем описании манифеста. Список типов содержит запрос на получение событий, а не перечень событий, которые генерирует плагин. Отсутствие `events` не означает подписку на все события.

Для посещаемости нужны:

| Тип | Для чего используется |
| --- | --- |
| `participant.joined` | Начать новый интервал присутствия участника. |
| `participant.left` | Закончить текущий интервал присутствия. |
| `call.ended` | Закончить оставшиеся интервалы и обработку звонка. |

Типы должны совпадать с каталогом источника; `call.ended` является событием звонка. События медиа и чата для посещаемости не запрашиваются. В общем формате сохраняется возможность объявлять другие типы, например `media.audio_muted` и `interaction.chat_message_received`.

Адрес источника событий нужен backend плагина, но относится к конфигурации платформы, а не к описанию плагина. Платформа передаёт gRPC target streamapi, настройки TLS и необходимые параметры доступа при запуске активации. Backend создаёт соединение с этим target и вызывает `EventService.Subscribe` с `callId` и разрешёнными фильтрами. Формат сообщения запуска задаётся контрактом управления активациями; эти параметры не становятся полями манифеста.

Например, существующая конфигурация демо использует `calls.vareonix.cc:443` с TLS снаружи стенда и `nginx:19090` без TLS внутри docker-сети prod. Это варианты подключения к одной инфраструктуре в разных условиях, а не разные свойства версии плагина. Текущее чтение target из `attendance.streamapi.target` при платформенной интеграции заменяется параметрами конкретного запуска.

В прежнем описании `event-url` обозначал HTTP-адрес backend плагина, куда платформа отправляет события. В целевом gRPC-контракте этот обработчик отсутствует. Поле удалено; переиспользовать его имя для адреса streamapi нельзя из-за противоположного направления подключения. `control-url` остаётся адресом backend плагина для управляющих сообщений.

## Медиа

`backend.media.input` и `backend.media.output` — необязательные списки со значением `[]` по умолчанию. Поддерживаются `AUDIO`, `VIDEO`, `SCREEN_SHARE`, `SCREEN_SHARE_AUDIO`.

Входящие медиа нужны плагину для обработки; исходящие означают запрос на публикацию медиа через платформу. Посещаемость не запрашивает ни те, ни другие: допускается опустить весь блок или передать пустые списки. Отсутствие блока или пустой список не означает доступ ко всем потокам.

## Результаты

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `backend.results.keys` | string[] | Да, если есть `results` | Непустой список ключей публикуемых результатов в формате `call.result`. |
| `backend.results.delivery-report-url` | string, URI | Нет | Абсолютный HTTPS-адрес для отчётов о доставке методом POST. Без поля отчёты на backend не запрашиваются. |

Посещаемость объявляет `attendance.summary`. Содержимое сводки определяется плагином; конкретные результаты, адресаты и ревизии в манифест не включаются. Разрешённые ключи проверяются в рамках конкретной активации.

Сообщение результата содержит `activationId`, `callId`, `messageId`, `recipients`, `key`, `revision` и `payload`. Адресаты дополнительно проверяются платформой. Повтор отправки сохраняет `messageId`; обновление результата увеличивает `revision`. Формат результата и отчёта о доставке относится к API обмена результатами.

Callback берётся из зарегистрированного манифеста. Произвольный `X-Callback-Url` из демо не является способом переопределения этого адреса в целевом контракте. Плагин проверяет отправителя отчёта и его принадлежность активации.

## Данные, передаваемые при запуске

В манифест не включаются:

- конкретные `activationId`, `callId`, `userId`, `participantId` и состав участников;
- выданные разрешения, адресаты результатов, роли и настройки конкретного подключения;
- адреса streamapi и Result Gateway, зависящие от окружения;
- токены, закрытые ключи, cookie stage и другие секреты;
- параметры демо: `fake`, адрес WireMock, локальные порты и таймаут остановки по запросам UI.

Платформа передаёт актуальные идентификаторы, разрешения, адреса сервисов и необходимые параметры доступа в проверенном контексте запуска. Публичные ключи и правила проверки доверия определяются общей конфигурацией интеграции. Отсутствие разрешения нельзя компенсировать прямым подключением плагина к инфраструктуре звонка.

## Файлы манифестов в репозитории плагина

Манифесты хранятся в каталоге `manifests/` внутри проекта плагина. Имя файла включает обе версии:

```text
manifest-v<manifest-version>_plugin-v<plugin-version>.json
```

Для посещаемости с форматом `1.1` и версией плагина `0.1.0` путь имеет вид `plugin-attendance/manifests/manifest-v1.1_plugin-v0.1.0.json`.

- Часть после `manifest-v` точно совпадает с `manifest-version` в JSON, часть после `_plugin-v` — с `plugin-version`.
- Версия формата меняется при изменении структуры или семантики контракта. Версия плагина меняется при выпуске его новой конфигурации или реализации.
- После публикации существующий файл не перезаписывают. Для следующей версии плагина, например `0.2.0`, добавляют `manifest-v1.1_plugin-v0.2.0.json`.
- При подготовке ещё не опубликованного манифеста его содержимое можно уточнять. Присутствие файла в репозитории не подтверждает готовность реализации или публикацию в реестре.
- Копию `manifest.json` в корне и псевдоним `latest.json` не поддерживаем: нужную пару версий выбирают явно по имени файла.

## Изменения относительно 1.0

- Добавлены `backend.control-url`, `backend.initial-state` и `backend.results`.
- Область подключения фиксирована общим правилом `per-call`; отдельного поля `activation.scope` нет.
- Для событий используется только gRPC. Поля `transport` и `event-url` отсутствуют; адрес streamapi и доступ к нему передаются при запуске активации.
- Описано событие `call.ended` и точный набор событий посещаемости.
- Версии SDK и блоки необязательных возможностей разрешено не указывать; отсутствие не даёт доступ к данным.
- Сохранены метаданные, `url-web`, `health-url`, типы медиа и приоритет конкретных типов событий над группами.
- Формат отделён от настроек окружения, данных конкретной активации и деталей демо.

Политики автоматической остановки, восстановление истории до активации и дополнительные команды звонка остаются за пределами этой версии.
